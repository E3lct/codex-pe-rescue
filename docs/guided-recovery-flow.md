# 引导恢复流程设计

目标体验：用户把仓库链接发给有本地工具能力的 AI，说明“帮我恢复”；AI 先查文件和已有信息，只在需要用户决定时提问。用户不需要安装 Skill、Git，填写 JSON 或修改代码。

## 通用程序与每次恢复的数据

程序不包含具体用户的路径。源备份、目标配置目录、所选聊天和新旧根目录对应表都是每次操作的输入。例如同一个程序可以处理 `D:\Projects\Sample → E:\Work\Sample`，也可以处理 `C:\Code\Sample → D:\Study\Sample`。配置变化不需要改源码、重新编译或为用户生成另一个安装包。

AI 负责理解需求、定位备份、识别聊天和新路径、解释预览并安排交接。引擎负责确定性的复制、会话解压、引用/偏移更新、合并、校验、备份与回滚。遇到新数据库版本或损坏格式才可能需要修改适配器，不能把这种情况当成普通路径变化。

## 顺序与分支

| 阶段 | AI/工具自动做什么 | 何时让用户回答 |
| --- | --- | --- |
| 0. 能力与意图 | 确认用户确实要求恢复；检查是否能访问本机、执行程序 | 只有链接而没有目的时问恢复还是了解；没有本机能力时说明只能指导 |
| 1. 识别材料 | 复用已提供信息，区分原始 `.codex`、已有迁移包、尚未找到备份 | 材料不明时显示简短选项；不要求上传备份 |
| 2. 定位与只读检查 | 检查用户指定目录、数据库、会话、当前目标初始化和运行环境 | 不知道备份路径才询问；缺 Python 时先找宿主已有运行环境 |
| 3. 确认恢复范围 | 展示项目/聊天候选，结合标题和目录定位；对比当前已有记录 | 未指定范围或有多个同名候选才问；内部 ID 由 AI 处理 |
| 4. 匹配新目录 | 验证未移动的目录；在用户指定的新项目范围内寻找候选 | 只对缺失/歧义对应项询问，不要求重填已确认路径 |
| 5. 生成方案 | helper 写私有配置、调用引擎准备并验证预览、生成启动文件 | 按用户审核规则展示具体方案后确认写入；失败时先解决实际阻塞 |
| 6. 独立执行 | 打开或提供双击启动文件，等待退出和 10 秒静默，再备份与安装 | 用户保存工作并完全退出 Codex；不让其手写命令 |
| 7. 核对结果 | 重新打开后读取已保存状态，检查回执、指定项目和聊天 | 只有 AI 无法查看界面时请用户确认指定内容是否出现 |

已有 `.rehome` 迁移包应使用相应工具的正式导入流程，不能改扩展名冒充原始备份。本工具当前针对原始离线配置；没有旧备份时不能承诺凭空重建本地聊天。

## 具体提问方式

宿主有结构化提问组件时优先使用；不支持时提供编号选项。一次集中询问当前真正缺少的信息，不把整个调查表一次性丢给用户。系统已知或文件可查的信息不问第二次。

**情形不明时：**

“你现在手上是哪种备份？”

- 从旧硬盘/PE 复制出来的 `.codex` 文件夹。
- 之前导出的 `.rehome` 迁移包。
- 不确定，先帮我确认。

用户已经说“系统进不去，从 PE 拷出了 `.codex`”时，跳过本题。

**范围不明时：**

“这次主要想恢复什么？”

- 先查看备份里有哪些项目和聊天。
- 恢复指定的几个项目。
- 找回某一段聊天。

用户已经说只找回一个学习聊天时，直接寻找候选，不建议全量导入。用户明确要求补回全部缺失记录时，先比对已有 ID，已存在且内容相同的列为保留；冲突或不支持的混合依赖单独报告，不批量覆盖。

**路径无法判断时：**

“备份里的 `D:\Projects\Sample` 在这台电脑对应哪个文件夹？”

- 提供已验证存在的候选目录。
- 保留原位置（只有目录实际存在才提供）。
- 尚未复制项目文件，先恢复文件再继续。

没有可靠候选时直接询问路径，不编造目录。多项映射可合并成一张小表让用户补充；已确认项不用重复问。不要只按文件夹同名就认定是同一个项目。

## 展示方案的内容

用普通语言展示：选中了哪些项目/聊天、数量、根目录从哪里变到哪里、当前已有记录如何保留、哪些内容暂不支持。用示例：

> 已找到你选择的 2 个项目、6 段主聊天。项目文件对应的新位置已确认。此次仅补入所选旧记录，保留当前已有聊天和登录配置；图片附件尚未由本工具恢复。已生成预览和启动文件，写入前会再备份当前数据。

数字必须来自实际预览，不使用固定示例替代。审核按钮可为“按此方案恢复”“调整选择”“先不恢复”。按用户已有授权规则决定是否需要这一步确认；不反复确认可逆的检查和准备。

## 文件形式与解包

原始 `.codex` 文件夹不需要整体解包。引擎把所需数据库与 sidecar 复制到隔离目录，从副本生成快照；选中聊天的 `.jsonl.zst` 会解压为可重新计算偏移的 JSONL，普通消息正文保持原样。

如果用户保存的是 ZIP 等外层压缩包，应先列出条目并检查绝对路径、目录穿越、链接和空间，再提取到独立私有目录，不直接解到当前 `.codex`，不覆盖原包。现有 helper 不提供通用外层压缩包解包命令；AI 可调用合适的已安装工具，或明确指出该步骤尚需处理。

## 运行环境与分发方案

| 入口 | 当前状态 | 用户是否需要另装 Python |
| --- | --- | --- |
| 仓库链接交给 AI | 已提供首页指引与 helper | AI 优先使用本机/宿主 Python 3.11+；都没有才需要补充 |
| 安装 Skill 后调用 | 可选，使用同一个 helper | 同上；不再要求单独下载项目或安装 Git |
| 手动 CLI | 已提供 | 需要 Python；供希望手动操作的人使用 |
| 自带运行环境的 Windows x64 便携 EXE | 本地候选构建已具备，尚未正式发布；需要干净系统验收 | 候选包自带 Python 与压缩依赖，不要求另装 |

AI 引导仍是主要入口，核心逻辑与用户输入分离。Windows x64 单文件候选把解释器、恢复核心和压缩依赖一起分发，并保留现有命令入口、选择输入和机器可读结果。AI 与图形界面若未来开发，应共用同一份恢复计划，不维护两套恢复算法。

打包不等于增加数据兼容性。正式发布候选前还需验证：没有系统 Python 的干净 Windows、中文/空格路径、离线使用、压缩会话、等待客户端退出、故障恢复、依赖许可与实际分发内容。当前本地构建会运行命令行冒烟检查，但这不能替代上述干净系统与完整写入测试；不把 Python wheel 或源码 ZIP 称为“免安装 EXE”。

对照参考：ReHome 目前提供内置核心的 Desktop App，并保留独立 Skill；其正常迁移流程是源端导出 `.rehome` 再在目标端导入。参见 [ReHome 项目说明](https://github.com/CalebYcj/codex-rehome) 与 [桌面构建配置](https://github.com/CalebYcj/codex-rehome/blob/main/desktop/src-tauri/Cargo.toml)。本项目侧重原系统不可启动、仅剩原始备份时的选择性恢复，不能据此宣称普遍优于 ReHome。

## 中断与完成的界限

双击启动后，窗口会等待、显示进度并在结束时暂停。用户不需要“退出后还要回来告诉 AI 已退出”。`result.json` 和回执保存实际结果；后续 AI 读取 `status` 接续。

`complete` 才是引擎写入成功；用户实际打开指定聊天才完成可见性核对。超时未写入可重新启动。已完成操作再次启动不会重复写入。失败状态必须先检查保存的错误/备份，再决定下一步；不能反复双击覆盖证据，更不能把部分写入误报为恢复成功。
